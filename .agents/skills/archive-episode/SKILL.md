# 单期项目归档

## 目标与写入边界

把用户已经确认的本期结果固化到真实单期 README，然后把同一项目交给后续三个记忆技能。

- 只修改当前真实项目的 `README.md`，不修改 `memories/`。
- `project/example/README.md` 永远只是模板，不得归档或作为真实事实源。
- 用户表达“本期正式归档，并开始整理记忆”的同等含义即可触发；不要求固定标点或逐字一致。
- 触发语本身已经批准本次 README 归档，不再重复询问是否归档。
- 不从聊天、旧记忆或 Git 提交中猜测缺失事实。

执行前完整读取：

- [归档工作流契约](references/workflow-contract.md)
- [README Changelog 契约](references/readme-changelog-contract.md)

## 归档流程

### 1. 找到当前项目

1. 将仓库根目录解析为同时包含 `project/` 与 `memories/` 的最近祖先目录。
2. 扫描 `project/*/README.md`，排除 `project/example/README.md`。
3. 当前工作方式默认只有一个在制项目。没有真实项目时停止；意外发现多个未归档项目时也停止，不按修改时间猜测。
4. 读取 `episode_id`、基础信息、创作确认、发布结果、数据分析、Changelog 和文档索引。

### 2. 检查归档事实

归档前确认：

- 基础信息完整，`episode_id` 合法且稳定。
- 已发布项目具备最终标题、平台、公开链接、发布时间和时长。
- 未发布、取消或暂停项目具备终局原因和下一次复核动作。
- 数据分析中的结论有证据、状态和下一期动作；证据不足时只能标为待验证或无法判断。
- README 包含符合契约的 Changelog。

如有缺失，用一段直白的话一次列出最少需要补充的内容。不得填模拟值，也不得继续记忆整理。

### 3. 写入归档

校验通过后：

1. 将 `当前状态` 设为 `归档`。
2. 将创作确认表的归档行设为 `已确认`，填写当天日期和一句话归档结果。
3. 把本次对话中用户已经明确确认、且会影响本期或以后创作的重要决定写入 Changelog；只存在于聊天中的结论必须先在这里落盘。
4. 添加一条归档 Changelog；相同内容已经存在时不得重复添加。
5. 不修改其他阶段的确认结果，不补写未经确认的分析，不重排 README 其他章节。

写入后运行：

```powershell
rtk python -B -X utf8 .agents/skills/archive-episode/scripts/validate_memory_workflow.py --repo-root . --stage archive --episode <README路径>
rtk python -B -X utf8 .agents/skills/episode-memory-sync/scripts/validate_sync.py --repo-root .
```

验证器只读。出现错误时，撤销本步骤刚写入且尚未通过验证的内容，保留错误说明并停止。

### 4. 唯一正常暂停点

归档成功后，只用日常语言说明已经完成什么，并询问：

> 本期项目已经归档。下一步会整理它的基本信息、发布结果和表现记录。要继续吗？

不要展示 Skill 名、脚本名、字段名、路径、预览编号或校验术语。

- 用户明确回答 `Y`、`是`、`继续`或同等含义时，按工作流契约生成内部交接，并立即执行 `episode-memory-sync`。
- 用户拒绝或暂缓时停止；README 归档保留，后续可从该项目继续。
- 出现资料缺失或写入错误时可以提出阻断问题；这不属于正常批准点。

## 完成条件

本技能完成仅表示：单期 README 已归档、Changelog 可追溯、只读检查通过，并已得到是否进入下一步的答复。不得把它描述为四份长期记忆已经整理完成。
