# 归档与记忆整理工作流契约

本契约是四个 Skills 的共同流程规则。各 Skill 保持自己的写入范围，但必须用同一种证据、批准、交接和恢复方式。

## 固定顺序

```text
archive-episode
  -> episode-memory-sync
  -> creative-memory-sync
  -> channel-decision-sync
  -> 最终完整性检查
  -> 用户确认整体完成后才允许 Git commit
```

不得跳过某份记忆的审计。某一步没有新增内容时仍要说明，并在用户同意后进入下一步。

## 证据顺序

1. 真实单期 README 中已确认的事实和 Changelog。
2. Changelog 明确指向的最终大纲、最终文稿、数据或其他本期文件。
3. Git 记录只能证明文字或文件发生过变化，不能用来猜测修改原因。

聊天不能成为长期记忆的唯一依据。重要聊天结论必须先由 `archive-episode` 写入 Changelog，后续技能才能使用。长期记忆也不得反向补全 README。

## 每步批准

- 每个 Skill 在正常路径中只暂停询问一次。
- 询问前先说明准备记录什么、依据是什么、哪些内容因证据不足不会记录。
- 使用日常语言，不显示 Skill 名、Schema、哈希、事务、同步范围、校验器或其他技术术语。
- 只有当前恰好存在一个待答问题时，`Y`、`是`、`继续`等简短答复才算批准。
- 批准后立即写入当前 Skill 负责的目标并回读检查，然后自动进入下一个 Skill。
- 用户可以只批准当前 Skill 所列内容的一部分；未批准部分保持不变。

## 内部交接

内部交接至少携带以下内容，但不得原样展示给用户：

```yaml
workflow: episode-memory-archive-v1
episode_id: WF-YYYYMMDD-NN
readme: project/<目录>/README.md
completed_stage: <刚完成的 Skill>
next_stage: <下一个 Skill>
approved_scope: <本步实际获批内容>
```

下一个 Skill 必须重新读取 README 和自己的目标文件，不得把交接内容当成事实源。直接调用某个记忆 Skill 时，如果没有工作流交接，就完成自身任务后停止，不擅自启动后续 Skill。

## Changelog 回写

- 每次成功修改长期记忆后，在本期 README 的 Changelog 追加一条 `记忆写入` 记录，说明写入了哪类内容及依据。
- 没有新增内容、用户拒绝或证据不足时不写 Changelog。
- Changelog 回写与当前记忆写入属于同一步；任一写入未通过检查，当前步骤不得留下半成品。
- 不得修改 Changelog 中已有的用户决策来迁就长期记忆。

## 经验升级

- 用户明确说出的长期要求可以立即作为候选，但仍需对应 Skill 批准。
- 只在一个项目中观察到的修改标为待观察，不扩写成永久偏好。
- 同一模式由三个不同 `episode_id` 支持后，才可询问是否升级为长期规则。
- 一次否决只适用于当时场景，除非用户明确宣布为长期禁用规则。

## 无变更、阻断与失败

- 无新增、重复内容或证据不足：不写文件，直白说明，并询问是否继续下一步。
- 用户拒绝：停止流程，保留此前已经批准且检查通过的结果。
- 写入或回读检查失败：恢复当前步骤开始前的目标内容，停止整个流程，修复后从该步骤继续。
- 与本期无关的历史问题：只报告，不在例行归档中顺手重写。

## 最终完成

最后一个 Skill 必须确认四份记忆均已审计，并列出每份文件的结果：已更新、无变更、用户未批准或阻断。全部检查结束后，回到主流程，用直白语言询问用户是否确认整体完成且允许保存版本记录。只有用户再次明确批准后才可提交 Git。
